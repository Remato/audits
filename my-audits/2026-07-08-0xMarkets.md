# [H-1] Insurance fund drained by pool drawdown that counts LP withdrawals as losses

> Status: Fixed

The per-market insurance fund injects capital into the pool when a market suffers a "drawdown". The drawdown is measured on the absolute pool value and is never normalized by the market-token (GM) supply:

```solidity
// InsuranceFundUtils.getDrawdownFraction (:63, :84-86)
int256 cur = MarketUtils.getPoolValueExcludingUnrealizedPnl(dataStore, market, prices, false);
...
uint256 drawdownUsd = epochPoolValueUsd - currentPoolValueUsd;
drawdownFraction = (drawdownUsd * Precision.FLOAT_PRECISION) / epochPoolValueUsd;
```

`getPoolValueExcludingUnrealizedPnl` is `poolAmount * price` per token. GM deposits and withdrawals mutate exactly this `poolAmount`. Therefore a liquidity provider withdrawal, a pure capital outflow where pool value AND GM supply both fall proportionally, so the per-share value is unchanged and there is no loss is measured as a "drawdown"

Once the (bogus) drawdown exceeds the per-market trigger (2% in `config/markets.ts:380`), the next decrease order, permissionlessly triggerable by closing any position, calls `attemptInjectPool`, which transfers reserve tokens from the `InsuranceVault` into the pool and credits the pool balance without minting any GM:

```solidity
// InsuranceFundUtils.attemptInjectPool (:245-255)
vault.transferOut(pnlToken, market.marketToken, injectedAmount);
MarketUtils.applyDeltaToPoolAmount(dataStore, eventEmitter, market, pnlToken, injectedAmount.toInt256());
```

> Pool value rises, GM supply is unchanged, so every remaining GM holder's share price jumps and captures the injected insurance capital

## Impact

1 - Any routine LP withdrawal larger than 2% of the weekly epoch snapshot drains the insurance reserve into GM holders with zero real bad debt

2 - An attacker holding GM triggers a large pool outflow, forcing a large injection (up to the entire reserve, `injectedAmount = min(requested, reserveBalance)`), then redeems their GM at the inflated share price, capturing the injected reserve. This is a direct, permissionless drain of protocol funds

## Steps to reproduce

1 - Seeds a market with 2,000 WETH of pool and mints 2,000,000 GM (share price = 1.0)
2 - Snapshots the epoch baseline and enables the 2% trigger (as config/markets.ts does)
3 - Funds the insurance reserve with 1,000 WETH
4 - Performs a 40% LP withdrawal, pool and GM supply both -40%, so per-share value is unchanged (no loss). The drawdown metric nonetheless reads 40%
5 - Calls attemptInjectPool

The attacker's deposit is fully recovered and they walk away with a net profit equal to the entire insurance reserve

> This is a permissionless, single-transaction-sequence, closed-loop theft of protocol funds

## Recommended fix

Measure drawdown on a per-share basis: compare `poolValue / marketTokenSupply` at the epoch snapshot against `poolValue / marketTokenSupply` now, so LP mint/burn cancels out and only genuine losses (realized PnL / fees) register as drawdown


# [H-2] Deposit/lock paths mint zero shares for non-zero principal (zombie lock position)

> Status: Fixed

The parent deposit/lock path computes shares with a plain round-down and never checks the result for zero:

```solidity
// CarthaParentVault._convertToShares (:130-134)
function _convertToShares(uint256 amount) internal view returns (uint256) {
    uint256 supply = totalSupply();
    uint256 total = totalAssets();
    if (supply == 0 || total == 0) return amount * 1e12;
@>  return (amount * supply) / total;   // rounds DOWN, can be 0 when amount*supply < total
}
```

```solidity
// CarthaParentVault._pullMintAndDistribute (:557-562)
function _pullMintAndDistribute(uint256 amount) internal returns (uint256 shares) {
    shares = _convertToShares(amount);     // can be 0
    SafeERC20.safeTransferFrom(IERC20(asset()), msg.sender, address(this), amount); // pulls FULL principal
    _mint(msg.sender, shares);             // mints 0
    _distributeToChildren(amount);         // principal forwarded to children
}
```

`totalAssets()` includes the parent's raw USDC balance `total += IERC20(asset()).balanceOf(address(this))`, so a direct USDC transfer into the vault inflates `totalAssets()` while `totalSupply()` is unchanged. A subsequent small deposit then satisfies `amount * supply < totalAssets()` and `_convertToShares` returns 0, yet the principal is still pulled and a lock position is written with `lockedShares = 0`, `lockedAmount = amount`.

The result is a zombie `LockPosition{exists:true, lockedAmount>0, lockedShares:0}` whose on-chain claim on the vault is zero

A deposit accepts principal but returns no ownership. It is also internally inconsistent, the legacy withdraw path guards exactly this ("no value moved" case) at :161 `if (payout == 0 && assets > 0) revert InsufficientVaultBalance();`, but the deposit/lock paths do not guard `shares == 0`

## Impact

- The deposit/lock functions produce a wrong result, a non-zero principal is taken for zero shares, writing a position that can never be redeemed for value `_convertToAssets(0) == 0`

- The stranded principal raises the share price of every other holder, so under an adversarial setup it is a value transfer from the stranded depositor to existing holders

## Recommended fix

Add a one-line guard so a deposit can never take principal for zero shares (defense-in-depth that holds even if minimumLockAmount is lowered), in every deposit/lock path:

```solidity
   // CarthaParentVault._pullMintAndDistribute, CarthaVault._createPosition, both lockTopUp paths
   shares = _convertToShares(amount);
+  if (shares == 0) revert InvalidAmount();   // never mint 0 shares for a non-zero deposit
```

Optionally adopt OpenZeppelin ERC4626 virtual shares/assets (or seed dead shares on the first deposit) for stronger inflation resistance, and add a sane lower bound to `setParentMinimumLockAmount / setMinimumLockAmount`



# [M-1] baselineSwap funding is charged at 2x the configured rate on single-collateral markets

> Status: Fixed

`getNextFundingAmountPerSize` compensates the organic funding amount for the single-collateral double-application by dividing it by divisor (= 2 when `longToken == shortToken`):

```solidity
    // MarketUtils.sol:1063-1064
    cache.fundingUsd = Precision.applyFactor(cache.sizeOfLargerSide, cache.durationInSeconds * result.fundingFactorPerSecond);
    cache.fundingUsd = cache.fundingUsd / divisor;      // organic funding is /divisor-corrected
```

The custom `baselineSwap` term is added after, without the `/divisor` correction:

```solidity
    // MarketUtils.sol:1072-1079
    uint256 baselineSwapUsd = Precision.applyFactor(
        swapLongsPayShorts ? cache.shortOpenInterest : cache.longOpenInterest,
        cache.durationInSeconds * swapPerSecond
    );
    if (result.longsPayShorts == swapLongsPayShorts) {
@>  cache.fundingUsd += baselineSwapUsd;            // NOT /divisor
}
```

Both `fundingUsd` and `baselineSwapUsd` then flow through the same downstream per-size split, which double-applies on single-collateral markets (see the code's own comment at :1035-1062). The organic term is pre-divided to cancel this; the baseline term is not, so it is charged at **exactly 2x**

`getPoolDivisor` returns 2 whenever `longToken == shortToken`. Every forex/synthetic market, exactly what `baselineSwap` is documented for is single-collateral: USDC/USDC at config/markets.ts:521-553 and USD0/USD0 at :560-654 (EUR, GBP, GOLD, XAG, JPY, WTI, WBTC, WETH, TAO)

So on every market `baselineSwap` is designed to run on, the baseline funding is deterministically doubled. (The config's crypto-perp markets e.g. WETH/USDC, WBTC/USDC, WETH/USDT at :705-725 are dual-collateral, divisor == 1, and are not `baselineSwap` targets, so they are unaffected)

## Impact

The custom baseline funding is silently applied at twice the configured rate on every single-collateral (forex/synthetic) market i.e. every market the feature is designed for. Funding is a value transfer in-motion between longs and shorts; at 2x, the receiving side extracts twice the intended value from the paying side each settlement, systematically mispricing those positions and accelerating unfair liquidations on the paying side. A trader can position on the receiving side to collect the doubled rate

## Recommended fix

Apply the divisor to the baseline term as well, e.g. `cache.fundingUsd += baselineSwapUsd / divisor` or fold `baselineSwapUsd` into `cache.fundingUsd` before the division



# [M-2] OrderHandler.updateOrder omits reversed-market price inversion, corrupting trigger/acceptable price on reversed markets

> Status: Fixed

0xMarkets supports "reversed" markets (a 0xMarkets-specific flag stored per market and baked into the market CREATE2 salt). For a reversed market, `OrderHandler.createOrder` converts user-supplied prices into the protocol's internal "real-index" price space by inverting `triggerPrice` and `acceptablePrice` (price -> 1e60 / price) and flipping isLong, before the order is stored. The order-execution path never re-inverts: it compares the stored price directly against `oracle.getPrimaryPrice(indexToken)`

`OrderHandler.updateOrder` does NOT perform this inversion. It writes the user-supplied `triggerPrice` and `acceptablePrice` verbatim. As a result, after a user updates a limit/stop order on a reversed market, the order's trigger and acceptable prices are left in user space while execution evaluates them in real-index space. The 2 spaces differ by a factor of price^2, so the order no longer behaves as the user intended:

- The trigger condition is evaluated against the wrong number (it can fire at an unintended price or never fire)
- The `acceptablePrice` slippage bound is meaningless, so the order either becomes unexecutable (`OrderNotFulfillableAtAcceptablePrice` on every attempt, i.e. a resting order that can never fill and whose collateral stays locked until the user cancels) or it executes with no effective slippage protection (a fill far worse than the user authorized)

## Root cause

`createOrder` inverts for reversed markets:

```solidity
// OrderHandler.sol:50-62
if (market.reversed) {
    if (params.numbers.triggerPrice != 0) {
        params.numbers.triggerPrice =
            Precision.mulDiv(Precision.FLOAT_PRECISION, Precision.FLOAT_PRECISION, params.numbers.triggerPrice);
    }
    if (params.numbers.acceptablePrice != 0) {
        params.numbers.acceptablePrice =
            Precision.mulDiv(Precision.FLOAT_PRECISION, Precision.FLOAT_PRECISION, params.numbers.acceptablePrice);
    }
    params.isLong = !params.isLong;
}
```

`updateOrder` writes the values raw, with no reversed handling:

```solidity
// OrderHandler.sol:135-137
    order.setSizeDeltaUsd(sizeDeltaUsd);
@>  order.setTriggerPrice(triggerPrice);       // user space, not inverted
@>  order.setAcceptablePrice(acceptablePrice); // user space, not inverted
```

The execution path consumes the stored values directly and never re-inverts for reversed markets

## Impact

- Reachable by an unprivileged actor (the order owner) through the normal user entry point `ExchangeRouter.updateOrder`, on a market type that is already live on-chain (a reversed market is deployed and active on Base Sepolia)
- The user's slippage protection `acceptablePrice` is silently voided after an update, the order can fill at a price the user never authorized -> loss of user funds in-motion
- Alternatively the order can no longer satisfy its `acceptablePrice` check and becomes unexecutable -> the user's resting limit/stop order never fires and its committed collateral stays locked until cancelled (temporary freezing / functional failure of the order)

## Steps to reproduce

1 - A reversed market exists onchain **0x8C1bFbC4026dC63e2C04962264007b2c57e20314**
2 - A user creates a LimitDecrease (or StopLossDecrease / LimitIncrease) order on it via `ExchangeRouter.createOrder`, the order is stored with inverted `triggerPrice/acceptablePrice`
3 - The same user calls `ExchangeRouter.updateOrder(key, sizeDeltaUsd, acceptablePrice, triggerPrice, ...)` with the same user-space prices a UI would supply
4 - The stored triggerPrice/acceptablePrice are now the raw (un-inverted) user-space values
5 - At execution, `validateOrderTriggerPrice` and the acceptablePrice slippage check compare these user-space values against the real-index oracle price, so the order misbehaves (wrong/never trigger, voided slippage bound, or unexecutable)

## Recommended fix

Apply the same reversed-market inversion in updateOrder that createOrder uses. Re-read the order's market and invert when reversed:

```solidity
if (order.market() != address(0)) {
    Market.Props memory market = MarketUtils.getEnabledMarket(dataStore, order.market());
    if (market.reversed) {
        if (triggerPrice != 0) {
            triggerPrice = Precision.mulDiv(Precision.FLOAT_PRECISION, Precision.FLOAT_PRECISION, triggerPrice);
        }
        if (acceptablePrice != 0) {
            acceptablePrice = Precision.mulDiv(Precision.FLOAT_PRECISION, Precision.FLOAT_PRECISION, acceptablePrice);
        }
    }
}
order.setSizeDeltaUsd(sizeDeltaUsd);
order.setTriggerPrice(triggerPrice);
order.setAcceptablePrice(acceptablePrice);
```

Add a regression test that creates and then updates an order on a reversed market with identical user-space prices and asserts the stored values are identical (both inverted) after each call


# [M-3] Config.setPythLazerFeed writes feed config to data-stream storage keys, PythLazerFeedProvider always reverts (Pyth Lazer oracle unconfigurable)

> Status: Fixed

`Config.setPythLazerFeed` is the only privileged entry point to configure a Pyth Lazer price feed for a token. It writes the feed id, inverted flag and multiplier into the DATA STREAM key namespace, but `PythLazerFeedProvider.getOraclePrice` reads them from the PYTH LAZER key namespace. These are derived from different base constants (different storage slots), so the values the provider needs are never written. Every price fetch through the Pyth Lazer provider then reverts, so any market priced by it cannot execute orders, liquidations, deposits or withdrawals (all flow through `Oracle.setPrices` -> the provider). 

A Secondary effect: writing the id to `dataStreamIdKey(token)` collides with the Chainlink Data Stream config for the same token (setDataStream and setPythLazerFeed share that slot)

## Root cause

`setPythLazerFeed` writes to data-stream keys (parameter names say "pythLazer", keys say "dataStream"):

```solidity
// contracts/config/Config.sol:153-156
dataStore.setBytes32(Keys.dataStreamIdKey(token), pythLazerFeedId);              // wrong key + wrong type
dataStore.setBool(Keys.dataStreamInvertedKey(token), pythLazerFeedInverted);     // wrong key
dataStore.setUint(Keys.dataStreamMultiplierKey(token), pythLazerFeedMultiplier); // wrong key
dataStore.setUint(Keys.pythLazerFeedSpreadFactorKey(token), pythLazerFeedSpreadFactor); // correct
```

The provider reads the Pyth Lazer keys:

```solidity
    // contracts/oracle/PythLazerFeedProvider.sol:34-38
    uint32 feedId = uint32(dataStore.getUint(Keys.pythLazerFeedIdKey(token)));
@>  if (feedId == 0) revert Errors.EmptyPythLazerFeedId(token);      // reverts here first
    uint256 feedMultiplier = dataStore.getUint(Keys.pythLazerFeedMultiplierKey(token));
    if (feedMultiplier == 0) revert Errors.EmptyPythLazerFeedMultiplier(token);
```

The namespaces are distinct: `DATA_STREAM_ID = keccak256(abi.encode("DATA_STREAM_ID"))` vs `PYTH_LAZER_FEED_ID = keccak256(abi.encode("PYTH_LAZER_FEED_ID"))` (and likewise for MULTIPLIER), with each per-token `key = keccak256(abi.encode(BASE, token))`. So after `setPythLazerFeed`, `pythLazerFeedIdKey(token)` and `pythLazerFeedMultiplierKey(token)` stay 0 and `getOraclePrice` reverts `EmptyPythLazerFeedId`

There is also a type mismatch: the setter stores the id with setBytes32 while the provider reads getUint(...) cast to uint32

## Steps to reproduce

1 - As CONFIG_KEEPER: `Config.initOracleProviderForToken(token, PythLazerFeedProvider)`, then `Config.setPythLazerFeed(token, feedId, false, multiplier[, spreadFactor])`
2 - Read DataStore: `pythLazerFeedIdKey(token) == 0` and `pythLazerFeedMultiplierKey(token) == 0` (never set), `dataStreamIdKey(token) == feedId` and `dataStreamMultiplierKey(token) == multiplier` (wrongly written)
3 - Trigger any price fetch for the token (submit + execute an order, or call the provider directly): `getOraclePrice(token, data)` reverts `EmptyPythLazerFeedId(token)`
4 - The Pyth Lazer oracle cannot be configured through its only setter, so any market relying on it is inoperable, and the token's data-stream slot is corrupted

## Recommended fix

Write the Pyth Lazer keys the provider actually reads, and reconcile the id type:

```diff
- dataStore.setBytes32(Keys.dataStreamIdKey(token), pythLazerFeedId);
- dataStore.setBool(Keys.dataStreamInvertedKey(token), pythLazerFeedInverted);
- dataStore.setUint(Keys.dataStreamMultiplierKey(token), pythLazerFeedMultiplier);
+ dataStore.setUint(Keys.pythLazerFeedIdKey(token), uint256(uint32(uint256(pythLazerFeedId))));
+ dataStore.setBool(Keys.pythLazerFeedInvertedKey(token), pythLazerFeedInverted);
+ dataStore.setUint(Keys.pythLazerFeedMultiplierKey(token), pythLazerFeedMultiplier);
  dataStore.setUint(Keys.pythLazerFeedSpreadFactorKey(token), pythLazerFeedSpreadFactor);
```

Also change the `setPythLazerFeed` id parameter from bytes32 to uint256/uint32 so the stored type matches the read type, and add a test that calls getOraclePrice after `setPythLazerFeed` and asserts it does not revert
